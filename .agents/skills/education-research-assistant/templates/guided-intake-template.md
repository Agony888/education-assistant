# 完整工作流的自适应引导入口

## 一、定位

`guided` 是完整工作流的前置梳理入口，不是独立的简化功能。

```text
确定一个目标工作流
→ 自适应选择下一问题
→ 记录关键决定与冲突
→ 形成工作流输入包
→ 用户确认执行
→ 运行所选工作流全部阶段
→ 输出指定档位成果
```

直接式和引导式使用相同的工作流阶段、质量标准和最终交付物。

## 二、依赖文件

引导式必须联合使用：

- `knowledge/adaptive-guidance-bank.md`：问题优先级和动态分支；
- `templates/research-decision-log-template.md`：关键决定与变更传播；
- `templates/session-checkpoint-template.md`：保存与恢复；
- `knowledge/output-profiles.md`：最终成果档位；
- `templates/workflow-state-template.md`：阶段执行和交接。

## 三、进入方式

用户提出完整任务但未指定入口时，询问：

```text
你希望怎样完成？

A. 引导式：每次只确认一个关键问题，梳理完成后执行所选完整工作流。
B. 直接式：根据现有材料立即执行所选工作流全部阶段，缺失内容明确标注。
```

以下情况不重复询问：

- 用户明确要求“一步一步引导”；
- 用户明确要求“直接生成，不要提问”；
- 用户只要求一个单项结果。

## 四、会话状态

```yaml
guided_session:
  target_pipeline: ""
  final_deliverable: ""
  output_profile: "standard"
  status: "目标确认"
  readiness: 0
  confirmed: {}
  tentative: {}
  excluded_options: []
  conflicts: []
  missing: []
  active_decisions: []
  next_question: ""
  ready_to_run_pipeline: false
```

状态只使用：

- `目标确认`；
- `信息收集`；
- `关系校验`；
- `等待执行`；
- `执行工作流`；
- `已完成`。

## 五、确定目标工作流

用户未明确最终交付物时，只问一个目标问题：

```text
你希望最后得到什么？

A. 一篇论文的完整解析、筛选与 Obsidian 入库
B. 多篇文献的矩阵、分类综述和综述初稿
C. 从研究方向梳理到完整开题报告
D. 从论文题目梳理到研究问题、方法、目录和写作计划
E. 其他完整成果
```

对应：

| 最终目标 | 目标工作流 |
|---|---|
| 单篇论文解析与入库 | `paper-to-note` |
| 多篇文献综述 | `literature-review` |
| 开题报告 | `proposal-design` |
| 毕业论文整体设计 | `thesis-design` |

若用户只需要题目优化、问卷设计或一个综述段落，应退出完整流程，改用对应单模式。

## 六、自适应提问

每轮从候选问题中选择优先级最高的一项。判断维度：

1. 是否阻断后续流程；
2. 是否改变研究类型、方法或目录；
3. 是否解决当前冲突；
4. 是否能同时确定多个下游环节；
5. 用户是否容易回答。

优先顺序：

```text
阻断性冲突
→ 研究对象与边界
→ 核心问题
→ 数据与现实条件
→ 研究类型
→ 概念、理论或维度
→ 方法与工具
→ 成果档位和格式
```

每轮只问一个主问题。不要机械问完固定清单。

推荐格式：

```text
目前已经确认：……

接下来只确认一件事：……？

A. ……
B. ……
C. ……
D. 其他
E. 暂时不确定
```

## 七、回答处理

### 明确回答

- 写入 `confirmed`；
- 更新研究决策日志；
- 重新计算完成度；
- 根据影响选择下一问。

### 模糊回答

先用一句话归纳理解，再只询问是否准确。

### 不确定或跳过

- 写入 `tentative` 或 `missing`；
- 暂不连续追问同一问题；
- 若其成为阻断项，再使用更具体的选项询问。

### 回答导致路径变化

立即检查：

```text
研究类型
数据需求
方法与工具
理论或维度
论文目录
已确定研究问题
```

受影响决定标为“需复核”，不得保留明显冲突。

## 八、研究决策日志

必须记录会影响研究设计的决定：

- 目标工作流和最终交付物；
- 研究中心；
- 研究对象与边界；
- 核心概念；
- 研究问题；
- 研究类型；
- 数据来源；
- 理论或分析框架；
- 方法和工具；
- 目录类型；
- 用户明确排除的方案。

用户使用 `修改：字段=内容` 时，读取 `research-decision-log-template.md`，检查下游影响，而不是只改一个孤立字段。

## 九、成果档位

默认 `standard`。只有档位会明显影响最终交付时才询问：

```text
你希望最终成果达到哪种程度？

A. `outline`：只要框架和关键表格
B. `standard`：标准完整方案
C. `submission-ready`：可直接修改提交的正式稿
D. `review-ready`：正式成果加严格评审
```

材料不足时自动降级并说明原因。

## 十、用户控制指令

| 指令 | 行为 |
|---|---|
| `查看进度` | 展示已确认、暂定、冲突、缺失和完成度 |
| `修改：字段=内容` | 修改决定并检查下游影响 |
| `跳过` | 暂时跳过当前问题 |
| `不确定` | 标记为暂定 |
| `保存进度` | 输出可复制检查点 |
| `恢复进度` | 读取检查点继续 |
| `直接生成` | 切换到直接式，执行同一目标工作流 |
| `重新开始` | 清空状态并重新选择目标 |
| `结束引导` | 只总结当前信息，不执行工作流 |

## 十一、保存与恢复

用户输入 `保存进度` 时，使用 `session-checkpoint-template.md` 输出精简 YAML 检查点。

用户粘贴检查点并输入 `恢复进度` 时：

1. 检查目标工作流；
2. 恢复已确认、暂定、冲突和缺失信息；
3. 不重复询问已确认问题；
4. 继续下一问题或进入工作流；
5. 新信息优先于旧检查点，并记录变更。

不得声称在外部后台永久保存会话。

## 十二、完成度与执行条件

按关键字段计算完成度：

| 字段 | 权重 |
|---|---:|
| 最终交付物与目标工作流 | 15 |
| 研究对象与边界 | 15 |
| 核心问题 | 15 |
| 数据或材料来源 | 20 |
| 研究类型 | 10 |
| 概念、理论或分析维度 | 10 |
| 方法与分析方式 | 10 |
| 格式与限制 | 5 |

- 80—100：可以执行；
- 60—79：有条件执行，需标记假设；
- 40—59：只适合初步方案；
- 低于 40：继续引导。

数据或材料来源缺失时，不能标为完整可行。

满足最低条件后提示：

```text
关键信息已经基本齐全。接下来将执行【目标工作流】的全部阶段，并按【成果档位】输出。回复“执行”即可；也可以先查看进度、修改内容或保存进度。
```

收到“执行”后，不再继续零散提问。

## 十三、转入完整工作流

执行前形成：

1. 工作流输入包；
2. 有效研究决策摘要；
3. 暂定信息和必要假设；
4. 未解决冲突；
5. 成果档位。

然后运行所选工作流全部阶段，并完成一致性检查。

## 十四、禁止事项

- 不让用户一次填写一长串问题；
- 不重复询问已确认信息；
- 不先问抽象理论，再问现实问题；
- 不把固定问题清单机械问完；
- 不把模型建议自动记为用户已确认；
- 不在输入尚未梳理完成时反复生成完整报告；
- 不无限提问；
- 不因选择直接式而省略所选工作流阶段；
- 不把完成度分数当作论文质量分数；
- 不用正式语言掩盖证据和研究设计缺口。
